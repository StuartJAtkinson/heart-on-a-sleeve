- Alembic is set up (`backend/alembic/`, baseline migration `f652273fd930`, verified by `backend/tests/test_alembic_migrations.py`), and `backend/app/core/migrations.py` now has a `run_migrations()` that safely runs `alembic upgrade head` against either a fresh DB or one already bootstrapped by the old `create_all` path (it stamps to baseline first instead of re-running `CREATE TABLE` on existing tables — covered by `backend/tests/test_migrations_runner.py`, both scenarios pass). It's wired into `router.py`'s `lifespan()` but gated behind `Settings.use_alembic_migrations` (env var `USE_ALEMBIC_MIGRATIONS`), **default `False`**, so production behaviour is unchanged until a human flips it. Before setting `USE_ALEMBIC_MIGRATIONS=true` in the live Cloud Run env, verify against a copy/staging of the production Postgres/PostGIS DB first — the local tests only cover sqlite.
- `public/landing.html`'s `#auth-row` (lines 88-121) only ever renders a "Logout" link+email when already signed in — when logged out there is no "Sign in" link at all, only the "Start Creating" CTA (which routes to `/index.html`, whose auth guard then redirects to `/login.html`). The in-SPA nav (`src/app.ts:1779`) always shows an explicit `<a href="/login.html">Sign in</a>` when logged out. Decide: is landing.html's single-CTA funnel intentional (avoid cluttering the marketing page with a second entry point), or should it surface an explicit Sign-in link too, matching the SPA nav?
